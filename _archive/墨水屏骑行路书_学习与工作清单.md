# 墨水屏骑行路书设备：从零到上车的学习与工作清单

> 适用对象：学过计算机、有编程概念，但没碰过软硬件的新手
> 目标：做一块超薄墨水屏，贴在公路车车把上，滚动/翻页显示路书与补给提示，替代纸质贴纸路书；后续由小程序解析 GPX 自动生成提示并无线下发
> 预计周期：业余时间 6–10 周（MVP 可压缩到 3–4 周）

---

## 0. 先想清楚架构（这一步比写代码重要）

### 数据流

```
GPX 轨迹  →  GPX 解析 + 规则提取  →  路书卡片 JSON  →  渲染成 1-bit 位图  →  无线下发到设备  →  墨水屏显示
（手机/云端）      （小程序或脚本）                       （手机或云端）        （WiFi / BLE）        （ESP32）
```

### 给新手的核心建议：**服务端渲染，设备端只当"相框"**

这是整个项目最重要的架构决策，建议一开始就走这条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 设备端渲染（进阶） | 设备解析路书 JSON，自己画字、画图标 | 数据小、可交互 | 中文字库、布局代码全塞进固件，改一次界面就要重新烧录，对新手极痛苦 |
| **B. 服务端渲染（推荐先做）** | 手机/电脑把整屏画面渲染成 **1-bit 位图字节流**，设备只负责"收字节 → 刷屏" | 界面用 Python/JS 随便画，改版不用动固件；中文字体不是问题；设备代码 < 300 行 | 每次数据量大一点（2.9 寸 296×128 单色约 4.7KB，BLE 传几秒，完全可接受） |

### 产品定义：电子版 Pro Rider Stem Notes（不是缩小版 Garmin）

职业车手已经有 GPS 码表，却仍然在把立上贴一张小贴纸。这说明有一类需求是码表满足不了的：**一眼看到整条路线的关键事件与节奏**。

所以产品定位应该是 **Course Awareness（路线态势感知）**，而不是导航：

| | Garmin 码表 | 本设备 |
|---|---|---|
| 回答的问题 | 我在哪？往哪走？ | **接下来有什么？还有多远？要提前准备什么？** |
| 信息形态 | 地图 + 实时数据 | 关键事件时间轴 |
| 何时看 | 持续看 | 骑行中扫一眼 |

**核心是"事件（Event）"，不是"路线（Route）"**——这直接决定了 GPX 分析算法的目标：不是把 GPX 转成路线，而是从中**识别值得告诉骑手的事件**。

事件类型（借鉴环法 Roadbook 图例，但精简）：

| 事件 | 说明 | 自动识别难度 |
|---|---|---|
| `start` / `finish` | 起终点 |  trivial |
| `climb` | 爬坡，带 CAT 分级 | 中（需海拔滤波） |
| `feed` | 补给区 | 易（按距离规则或手工 wpt） |
| `sprint` | 冲刺点/分段计时 | 手工为主 |
| `danger` | 危险路段（陡降、发夹弯、石板路） | 中 |
| `turn` | 关键转弯 | 中（方位角） |

**三层显示结构**（对应状态机的三个状态）：

| 层级 | 回答什么 | 触发 |
|---|---|---|
| L1 主页面 | 下一个关键点是什么，还有多远 | 默认常驻 |
| L2 未来列表 | 后面还有什么，整体节奏 | 短按 NEXT |
| L3 事件详情 | 这个爬坡多长多陡、要补什么 | 再按 NEXT |

**⚠ 图标必须自己画成单色位图。** 墨水屏是 1-bit 单色屏，emoji（⛰️🍼🟢）是彩色位图，缩放后糊成一团。请准备 24×24 或 32×32 单色图标：爬坡=▲、补给=水滴、冲刺=⚡、终点=格子旗、危险=感叹号三角、转弯=箭头。

**爬坡 CAT 分级（供 GPX 分析用，参考 Strava）**

```
score = 长度(km) × 平均坡度(%)
CAT4 ≥ 15 | CAT3 ≥ 30 | CAT2 ≥ 50 | CAT1 ≥ 80 | HC ≥ 120
```

前提：海拔必须先滤波（移动平均 + ±3~5m 死区），否则 GPS 海拔噪声会识别出几十个假爬坡。

UI 原型见 `StemNotes_UI原型.html`（可点击体验三层切换与时间轴推进）。

### 四个版本：别把"学习路径"和"产品架构"混为一谈

位图路线是 **V0/V1 的战术选择，不是终局架构**。分四步走，每一步都能实际用：

| 版本 | 数据流 | 状态 |
|---|---|---|
| **V0** | 一张 BMP → ESP32 → 墨水屏 | 硬件验证：屏幕、SPI、驱动、供电全通 |
| **V1** | JSON → **PC 渲染** → 位图 → ESP32 → 按键翻页 | 第一个能骑车的 MVP |
| **V2** | JSON → **ESP32 渲染**（子集化中文字库）→ 墨水屏 | 设备真正独立，数据极小 |
| **V3** | GPX → 自动分析 → JSON → BLE → 电子路书 | 完整产品 |

V2 才做设备端渲染，是因为到那时你已经知道自己真正需要什么样的 UI，而不是提前设计一个可能用不上的排版引擎。

**V1 的交互：不自动轮播。**
- 默认**保持当前页**（路书是"当前有效的指令"，被时间冲掉是危险的——你正在看"右转 800m"，屏幕不该自己变成补给提示）
- 短按 → 下一页；长按 → 上一页/返回
- 想做"自动"，正确方向是 **V3 基于位置自动翻页**（骑到 42.4km 自动从"右转 800m"切到"右转 200m"），而不是基于时间
- V2 后可加"距离倒计时"：只局部刷新数字区（如每 200m 更新一次），既不冲掉信息又有实时感

### 定时刷新：每 30 分钟唤醒一次

**这是"维护刷新"，不是"轮播"**——两件事要分清：

| 目的 | 唤醒后做什么 | 30 分钟是否合适 |
|---|---|---|
| **防残影（主要）** | 把当前页**重新全刷一遍**，内容不变 | 合适。甚至 10 分钟一次也行 |
| 推进路书（次要） | 切到下一页 | 不合适——6 小时骑行只有 12 次，而路书通常有 20–40 个提示点，翻不完 |

→ 结论：**定时器负责"保持画面干净"，按键/GPS 负责"翻页"**。两者不冲突，可以同时启用。

**功耗：这个决定几乎没有代价**

| 项目 | 估算 |
|---|---|
| 一次唤醒（启动 ~0.2s + 全刷 ~1.5s） | ≈ 0.01–0.02 mAh |
| 6 小时骑行 × 12 次 | ≈ 0.15 mAh |
| 占 500mAh 电池 | **约 0.03%，完全可忽略** |
| 即使改成 5 分钟一次（72 次） | ≈ 1 mAh，仍可忽略 |

所以间隔随便设，真正的约束只有两个：**全刷会闪一下**（骑行中会注意到，但无害）、**别冲掉当前信息**。

**实现要点（Arduino / ESP32-C6）**

```cpp
#include <esp_sleep.h>

#define SLEEP_US  (30ULL * 60 * 1000000)   // 30 分钟

void enterSleep() {
  esp_sleep_enable_timer_wakeup(SLEEP_US);           // 定时唤醒
  // 若按键在 GPIO0-7：esp_sleep_enable_ext1_wakeup(...)
  // 若用 light sleep：gpio_wakeup_enable(...) + esp_sleep_enable_gpio_wakeup()
  esp_deep_sleep_start();
}

void setup() {
  esp_sleep_wakeup_cause_t cause = esp_sleep_get_wakeup_cause();
  if (cause == ESP_SLEEP_WAKEUP_TIMER) {
    renderCurrentPage(/* fullRefresh = */ true);      // 维护刷新：全刷清残影
  } else {
    renderCurrentPage(/* fullRefresh = */ false);     // 按键唤醒：局部刷，快
  }
  enterSleep();
}
```

要点：
- 用 `esp_sleep_get_wakeup_cause()` 区分是**定时器**还是**按键**唤醒，决定全刷还是局部刷
- 全刷虽然闪，但能彻底清残影；有了 30 分钟定时全刷，就**不需要**再记"局部刷了几次要强制全刷"的计数器了
- 定时唤醒和按键唤醒可以**同时配置**，任一触发都会唤醒
- 当前页码存 RTC memory（deep sleep 不掉电）或 LittleFS

**V1 的其他边界：**
- 无 GPS、无实时速度、无传感器
- 电脑生成 N 张位图卡片 → USB 下发 → 存 Flash
- 按键翻页，其余时间睡眠

GPS 自动翻页、心率功率、离线地图等留到第二版，可参考开源项目 [OpenTrailPaper](https://github.com/RaemondBW/OpenTrailPaper)（LilyGO T5S3 + ESP32-S3 的完整骑行码表）。

### 为什么选墨水屏（也意味着要接受什么）

- 优点：阳光下越亮越清晰（这一点 LCD/OLED 在公路车上全跪）、静态画面 **零功耗**、断电画面不丢、对比度高
- 代价：刷新慢（全刷 1–2 秒，局部刷 0.3 秒左右）、刷新时会闪黑/白、**低温（<5℃）刷新变慢且对比度下降**、屏幕玻璃基底很脆怕压怕摔、长期显示同一画面会有残影（需要定期全刷清屏）

## 1.5 实际硬件：ESP32-S3 一体板（已确认）

**配置**：ESP32-S3（Xtensa LX7 双核 240MHz）· 1.54" 200×200 黑白墨水屏（SPI）· 8MB Flash + 8MB PSRAM · Wi-Fi + BLE 5 · 全刷 2s / 局部刷 0.3s · PCF85063 RTC · SHTC3 温湿度 · Micro SD · 音频编解码 · 锂电充放电管理 · PWR/BOOT 双按键。

比 C6 方案好很多，但有 7 条认知要更新：

**① 依然没有经典蓝牙（S3 也只有 BLE）**

⚠️ 这一条**不随芯片改变**：除 ESP32 经典款外，S3 / C3 / C6 / H2 全部只有 BLE。网上那些"蓝牙传图到墨水屏"的 SPP 例程（含微雪安卓 App）**都用不了**。
→ 无线下发只能 BLE 或 Wi-Fi。不过见 ⑤，V1 根本不需要无线。

**② 原生 USB，必须开 USB CDC On Boot**

S3 无 CH340/CP210x：好处是不用装驱动，坏处是 Arduino 里不把 `Tools → USB CDC On Boot` 设为 `Enabled`，`Serial.println()` **一个字都看不到**。上传后没反应就按一下 RESET。

**③ deep sleep 唤醒引脚放宽了**

S3 的 RTC GPIO 是 **GPIO0–21**（不是 C6 的 0–7），light sleep 更是任意数字 GPIO。→ 按键接哪**先看板上哪些脚空着**，不用提前立规矩。

**④ PSRAM 必须选对**

Arduino 里 `Tools → PSRAM → **OPI PSRAM**`，选错那 8MB 用不了（能编译，运行才崩）。

**⑤ Micro SD 卡槽是 V1 的最大捷径**

V1 完全不需要做数据传输：

```
电脑 Python 渲染页面 → 存 BMP → 拷进 SD 卡 → 插回板子 → 设备读取并翻页
```

不用写 USB 协议、不用写 BLE、不用做小程序。**V1 从"显示 + 翻页"直接可用**，工作量从几周压到几天。无线传输留到 V2。

**⑥ 单页数据量很小**

`200 × 200 ÷ 8 = 5000 字节/页`。8MB Flash 能存上千页，SD 卡更是没上限。所以"PC 渲染位图"这条路在这块板子上**完全没有存储压力**。

**⑦ 两个暂时用不上但值得记住的外设**

- **SHTC3 温湿度**：墨水屏低温下刷新变慢、对比度下降，有温度传感器就能做**温度补偿**（按温度调刷新参数），冬天骑车有用
- **PCF85063 RTC**：比内部计时器准，跨断电保持，将来做"出发后已用时"方便

**另外两条通用经验不变**：国内装 Arduino-ESP32 板卡包经常超时（用离线包或 PlatformIO 国内镜像）；先跑通**厂商 Demo** 再自己写代码，引脚和驱动类以厂商资料为准。

## 2. 阶段二：点亮屏幕（3–5 天）

### 概念先搞懂（一天足够）

| 概念 | 一句话解释 |
|---|---|
| SPI | 屏幕与主控的四线通信（SCK/MOSI/CS/DC），再加 RST、BUSY |
| 分辨率 & 缓冲区 | 296×128 单色 = 37888 像素 = 4736 字节，ESP32 内存放得下；大屏需要 PSRAM 或分块 |
| 全刷 vs 局部刷 | 全刷=闪一下、无残影、慢；局部刷=快、不闪、会有残影积累（刷几次要全刷一次） |
| LUT | 驱动波形表，决定刷新效果与温度补偿 |
| 三色屏 | 有红/黄第二色层，刷新一次要 10–20 秒，骑行场景**不推荐**，选纯黑白 |

### 常见的坑

- 屏幕不亮：先查供电（刷屏瞬间电流脉冲大，USB 口或电池电压跌落会导致异常，建议并联 100µF+ 电容）
- 花屏/白屏：驱动型号选错（SSD1680 / UC8151 / IL3820 别混）
- 屏幕发出异味或出现黑边：排线没插到底、或屏被压裂（墨水屏真的脆，建议**一次买两块**）

## 3. 阶段三：把"显示什么"设计对（1 周，最容易被忽略但决定成品体验）

骑行中用不上复杂功能，真正难的是**抬头 300ms 内读完**。

### 信息设计原则

- 主信息字号要大到 40km/h 手抖状态下能看清（2.9 寸屏上正文建议 ≥ 24px，关键数字 ≥ 48px）
- 一屏只说一件事：**"前方 3.2km 补给点（便利店）"** 就比一整张路线图有用
- 不要用灰度/抖动图片表示重点——1-bit 屏幕上会糊成一团
- 顶部放全程进度条（你现在在整条路线的哪里），底部放下一条提示，中间是主信息

### 任务清单

- [ ] **3.1** 定义路书卡片数据格式（JSON），建议这样：
  ```json
  {
    "route": "环千岛湖",
    "total_km": 128.4,
    "cards": [
      { "id": 1, "at_km": 0.0,  "type": "start",  "title": "出发 · 千岛湖广场", "sub": "沿淳杨线向南" },
      { "id": 2, "at_km": 32.5, "type": "turn",   "title": "200m 后左转", "sub": "进入 X712 县道" },
      { "id": 3, "at_km": 45.0, "type": "supply", "title": "补给点 1.2km", "sub": "汾口镇 · 便利店/加水" },
      { "id": 4, "at_km": 58.2, "type": "climb",  "title": "爬坡 4.8km", "sub": "平均 5.2% · 最高 420m" }
    ]
  }
  ```
- [ ] **3.2** 用纸和笔（或 Figma / draw.io）画出 3 种卡片板式：转弯卡、补给卡、爬坡卡
- [ ] **3.3** 写渲染脚本（Python + Pillow 最省事，或 Node + canvas），输入 JSON、输出每屏的 1-bit 字节流
- [ ] **3.4** 打包成二进制文件格式，建议一个极简格式：
  ```
  [magic 2B][version 1B][card_count 2B][index 2B][width 2B][height 2B][reserved]
  [card0: len 2B + payload][card1: ...]...
  ```
  预留 crC 校验和压缩位（位图用 RLE 或 zlib 能压到 1/5）
- [ ] **3.5** 把渲染好的卡片用 SD 卡或 USB 灌进设备，静态翻页看效果（先不碰无线）

## 4. 阶段四：交互、存储与功耗（3–5 天）

### 任务清单

- [ ] **4.1** 按键翻页：2 个按键（上一页/下一页）足够，接 GPIO，内部上拉
  - [ ] 软件消抖（20ms）或用外部 RC
  - [ ] 支持长按（回首页/清屏）
- [ ] **4.2** 用 ESP32 的 **深度睡眠（deep sleep）** 把功耗压下去
  - [ ] 关键：只有 RTC GPIO 能唤醒（S3/C3 与经典 ESP32 的可用引脚不同，务必查你的芯片手册）
  - [ ] 用 RTC memory 或 Flash/EEPROM 保存"当前第几页"
  - [ ] 目标：待机电流 < 100µA，一块 500mAh 电池能撑几周
- [ ] **4.3** 存储：卡面数据存 Flash（LittleFS / SPIFFS）或 SD 卡
  - [ ] LittleFS 上手简单，几十 KB 的路书数据绰绰有余
- [ ] **4.4** 供电
  - [ ] 电池容量估算：一次局部刷约 20–50mA × 0.5s，每天翻 100 次 → 续航以周计
  - [ ] 加低电量检测（ADC 分压测电池电压）并在屏幕上提示
  - [ ] 电池别过放（加保护板）
- [ ] **4.5** 残影管理：每刷 5–10 次局部刷后强制一次全刷；长时间不用时清屏再断电

## 5. 阶段五：无线下发（1–2 周，按难度递增顺序做）

**强烈建议按 USB → WiFi → BLE 的顺序推进**，不要一上来就啃小程序 BLE。

| 方案 | 难度 | 说明 |
|---|---|---|
| **A. USB 串口** | ⭐ | 先用串口把卡片数据灌进去，验证整条链路，半天能搞定 |
| **B. WiFi 网页上传** | ⭐⭐ | 设备上电开 AP 热点（或 SoftAP+WebServer），手机连上打开 192.168.4.1，上传文件。无需小程序，体验已经不错 |
| **C. 微信小程序 + BLE** | ⭐⭐⭐⭐ | 最终形态，但要先过 BLE 分包、MTU、小程序蓝牙权限几道坎 |

### 任务清单

- [ ] **5.1** USB/串口通道：写个 Python 脚本（`pyserial`）把打包好的 bin 发过去
- [ ] **5.2** WiFi 通道
  - [ ] ESP32 开 AP + `WebServer`，做一个最小上传页面（多选文件 + 进度）
  - [ ] 或反向：设备连家里 WiFi 后从本地 HTTP 服务拉取（OTA 式）
  - [ ] 上传后校验 CRC、写入 LittleFS、刷新屏幕
- [ ] **5.3** BLE 通道（为小程序做准备）
  - [ ] 学 BLE 基础概念：GATT / Service / Characteristic / Notify / MTU
  - [ ] 先用手机 App（Android: nRF Connect；iOS: LightBlue）连接调试，确认收发正常再写小程序
  - [ ] 设计简单协议：包头 + 序号 + 长度 + CRC，支持断点续传（BLE 默认 MTU 23 字节，需分包；可协商到 100+）
  - [ ] 数据量估算：4736 字节 / 200 字节每包 ≈ 24 包，几秒完成
- [ ] **5.4** 小程序（最后做）
  - [ ] 注册微信小程序账号（个人主体即可）、装微信开发者工具
  - [ ] 页面：选择 GPX → 预览生成的卡片 → 连接设备 → 下发
  - [ ] 小程序里解析 GPX 可用 `fast-xml-parser`；不能随便用 Node 库，注意体积限制（主包 2MB）
  - [ ] 备选：如果不想做小程序，做成**网页 PWA** 也行，但蓝牙要用 Web Bluetooth（iOS Safari 支持有限，安卓 Chrome 可以）

## 6. 阶段六：GPX 分析 → 自动生成路书（1–2 周）

这部分是纯软件，跟硬件解耦，可以并行做，而且**最容易做出成就感**。

### 先懂 GPX

```xml
<trk><trkseg>
  <trkpt lat="30.1234" lon="119.5678"><ele>120.5</ele><time>2026-09-07T06:12:03Z</time></trkpt>
  ...
</trkseg></trk>
<wpt lat="..." lon="..."><name>补给点</name></wpt>   <!-- 手工打点，优先使用 -->
```

### 提取规则（按价值排序）

| 提示类型 | 提取方法 | 关键阈值 |
|---|---|---|
| **补给点** | 优先用手工 `wpt`；否则按规则：每 30–40km 一个、连续爬坡前 2km 一个、长下坡结束后一个；再叠加 POI（高德/OSM 便利店）匹配 | 30–40km |
| **转弯** | 逐点算方位角（bearing），取前后各 ~30m 的平均方向做差，超过阈值且在路口处判定转弯 | 转角 > 45°；注意先做平滑，GPS 噪声会让角度乱跳 |
| **爬坡段** | 对 `ele` 做移动平均 + 死区滤波（±3~5m），识别连续上升段，输出长度/累计爬升/平均坡度 | 段长 > 500m 且爬升 > 30m |
| **危险提示** | 陡降（坡度 < -8%）、连续下坡长度 | 视路线而定 |

### 任务清单

- [ ] **6.1** 拿到 GPX：行者/黑鸟/Strava/Garmin Connect 导出，或用 [bikerouter.de](https://bikerouter.de) 规划后导出
- [ ] **6.2** 解析（Python 用 `gpxpy`，两行代码搞定；JS 用 `fast-xml-parser` 或 `@xmldom/xmldom`+xpath）
- [ ] **6.3** 实现距离计算：Haversine 公式依次累加（注意：GPS 采样点越密越准）
- [ ] **6.4** 实现爬坡识别（先滤波再分段，直接对原始数据分段会得到几十个"爬坡"）
- [ ] **6.5** 实现转弯识别（方位角 + 平滑 + 距离窗口）
- [ ] **6.6** 输出 cue sheet JSON（就是阶段三定义的格式）
- [ ] **6.7** 把 JSON 喂给阶段三的渲染脚本，出图 → 打印成 A4 纸，先贴在车把上真骑一次验证信息是否有用（**低成本验证，强烈建议做**）
- [ ] **6.8** 加人工微调界面：地图上手动增删补给点（可以用 [Leaflet](https://leafletjs.com) + 高德/OSM 瓦片）

## 10. 避坑清单（按踩中概率排序）

1. **数据线不带数据** → 串口连不上，先换线
2. **供电不足** → 刷屏瞬间电流脉冲导致复位/花屏，加电容、别用太细的线
3. **墨水屏碎/压坏** → 装壳前不要把它当纸片随手放；避免单手捏屏
4. **残影累积** → 定期全刷；长期不用前清屏
5. **低温刷新异常** → 冬天刷新变慢、发灰，属于正常物理特性，选低温型或做温度补偿
6. **深度睡眠唤醒引脚选错** → 只有 RTC GPIO 能唤醒，且 S3/C3/经典 ESP32 不一样
7. **BLE 分包丢数据** → 一定要加序号 + CRC + 重传，别指望一次成功
8. **小程序体积超限** → 主包 2MB 限制，字库/地图资源走网络加载
9. **电池过放** → 加保护板 + 软件低电量关屏
10. **一开始就想做完整系统** → 先做出能翻页显示三张卡片的版本，再迭代

## 11. 里程碑与验收标准

| 里程碑 | 验收标准 | 建议时间 |
|---|---|---|
| M1 环境通 | 串口能输出 Hello，能烧录 | 第 1 周 |
| M2 屏幕亮 | 屏幕上显示一张自定义 1-bit 位图（含中文） | 第 2 周 |
| M3 卡片对 | 三种路书卡片在屏幕上看得清、信息有用 | 第 4 周 |
| M4 能用 | 按键翻页 + 深度睡眠，装电池脱离电脑跑一天 | 第 5–6 周 |
| M5 无线 | 手机（WiFi 或 BLE）下发新路书到设备 | 第 7–8 周 |
| M6 自动生成 | 上传 GPX → 自动生成卡片 → 下发 → 上车 | 第 9–10 周 |
| M7 成品 | 3D 打印外壳 + 车把固定 + 防水，完成一次实际骑行 | 第 11–12 周 |

**M4 就是分水岭**——到了这一步，你已经可以用它真去骑车了，后面都是锦上添花。
