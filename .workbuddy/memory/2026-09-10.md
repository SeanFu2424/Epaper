## 电池模式白屏问题彻底定位并修复 ✅

### 现象回顾（卡了用户整整 3 次重传）

- 插 USB → 屏幕正常显示 `42.6 km`
- 拔 USB、按住 PWR 键开机 → 屏幕**完全白屏**（电池 90%，排除电量）
- 三次尝试都失败：`delay(2000)` → `delay(3000)` + SPI 降到 2MHz → 冷启动 deep sleep 3 秒

### 真因：这块板的电源键是【固件自锁】，不是 IP5306

从官方仓库 `waveshareteam/ESP32-S3-ePaper-1.54` 源码确认（**不是猜的**）：

`02_Example/Arduino/07_BATT_PWR_Test/user_config.h`：

```c
#define VBAT_PWR_PIN    GPIO_NUM_17   // BAT_Control
#define PWR_BUTTON_PIN  GPIO_NUM_18   // BAT_KEY
#define EPD_PWR_PIN     GPIO_NUM_6
#define Audio_PWR_PIN   GPIO_NUM_42
```

`src/power/board_power_bsp.cpp`：

```cpp
void VBAT_POWER_ON()  { gpio_set_level(vbat_power_pin, 1); }  // GPIO17 HIGH = 维持电池供电
void VBAT_POWER_OFF() { gpio_set_level(vbat_power_pin, 0); }  // GPIO17 LOW  = 断电关机
void POWEER_EPD_ON()  { gpio_set_level(epd_power_pin, 0); }   // GPIO6 LOW = 屏幕通电
```

`src/button_bsp/button_bsp.c`：`button2_active = 0` → **PWR 键按下时 GPIO18 = 低电平**（芯片内部上拉），
`BTN_LONG_PRESS_START` 事件用于关机。

官方 `user_app.cpp` 的 `user_app_init()` 第一行就是 `board_div.VBAT_POWER_ON();`。

### 失败机理

```
按住 PWR 键 → 硬件给板子通电（只在手指按着时成立）
    ↓
ESP32 启动，跑 setup()，但固件从未操作 GPIO17
    ↓
手指松开 → 没有任何东西维持供电 → 电源切断
    ↓
屏幕停在 SSD1681 上电复位后的全白状态 → 用户看到白屏
```

插 USB 时不白屏，因为 VBUS 直接供电，不走 GPIO17 自锁链路。
之前所有 delay / deep sleep 方案都不可能有用——**问题根本不在时序，而在电源压根没被锁住**。
（deep sleep 方案还会让情况更糟：GPIO17 在深睡时直接掉电平。）

### 修复（`00_HelloScreen/00_HelloScreen.ino` 重写）

```cpp
#define VBAT_PWR 17   // BAT_Control：HIGH=维持供电，LOW=断电关机
#define PWR_BTN  18   // BAT_KEY：按下=LOW

void setup() {
  // 第 1 件事，必须最先做
  pinMode(VBAT_PWR, OUTPUT);
  digitalWrite(VBAT_PWR, HIGH);

  pinMode(PWR_BTN, INPUT_PULLUP);
  delay(30);
  pwrHeldAtBoot = (digitalRead(PWR_BTN) == LOW);  // 用户是否按着它开机

  Serial.begin(115200);
  showText("42.6 km");     // 画一屏，居中，画完 hibernate + 关屏电
}

void loop() {
  // 开机 3 秒缓冲 + 等松手后武装 → 按住 1.5 秒 → 画 "OFF" → GPIO17 拉低断电
}
```

关键点（避免立刻自关）：
1. 开机后前 3 秒不响应按键
2. 若开机瞬间按键仍按着（用户按着它开机），必须等松手后才武装"长按关机"
3. 官方例程用 `is_vabtflag` 做同样的事

删除了：`esp_sleep.h` 冷启动 deep sleep、所有 `delay(2000/3000)`、SPI 2MHz 降速。

`第0步_先让屏幕亮起来.md`：

## 01_Paging 首烧反馈：4 个问题的定位与修复

用户实测反馈（9/10 15:04）：内容显示 10 页、能翻页，但有 4 个问题。

### ① 编译花了将近 1 小时 → 环境问题，不是代码问题

查出机器真实配置：**i5-4300U（2 核 4 线程）/ 3.9 GB RAM / C 盘只剩 11 GB**。
全量编译 ESP32 核心（2000+ 源文件）在这套配置上客观就慢。

从 IDE 自己的构建目录 `%LOCALAPPDATA%\arduino\sketches\<hash>` 取证：

| sketch | 构建时间 | 耗时 |
|---|---|---|
| `00_HelloScreen`（第二次） | 13:58→14:00 | **1 分 36 秒** |
| `01_Paging`（首次） | 14:27→14:58 | **31 分钟** |

→ **差别只在缓存有没有命中**。缓存键 = sketch 路径 + FQBN 全参数。
`01_Paging` 的 `core/` 目录居然是空的（`00_HelloScreen` 的有 59 个 .o + core.a）。

**发现的关键技巧**：FQBN 完全相同的两个 sketch，核心对象可以**跨目录复制复用**
（已把 `00_HelloScreen` 的 `core/*` 复制到 `01_Paging` 的 `core/`）。
另外确认 **arduino-cli 可以脱离 IDE 直接命令行编译**：
`%LOCALAPPDATA%\Programs\Arduino IDE\resources\app\lib\backend\resources\arduino-cli.exe`
（版本 1.5.1，支持 `--fqbn` / `--build-path`，输出英文更好读）

**顺便纠正一个记错的事实**：实际 `PartitionScheme=default`，**不是** Huge APP。FlashSize=4M。
（从 `build.options.json` 读出来的真值）

#### ⚠️ 当天晚些时候的实测把这些假设推翻了（重要）

我用 arduino-cli 在用户机器上真编了一遍：

- **完整编译 `01_Paging` = 41.6 分钟**，成功（Sketch 354184 B / 27%，Global 45872 B / 13%）
  → **我改的固件（中断按键 + xAdvance 精确折行）编译通过**
- 紧接着**什么都不改**再编一遍：超过 17 分钟还在跑，而且**构建目录里的 .o 被整个清空**
  （`core/` 目录消失、`libraries/` 只剩 105 个 `.libsdetect.d`、`.bin`/`.elf` 都没了）

→ **结论修正：arduino-cli / IDE 每次编译都会清空构建目录从头编。**
"缓存命中就秒编"、"复制核心对象就能复用"**两条都不成立**，第一条结论作废：

| 之前的推断 | 实测结果 |
|---|---|
| `00_HelloScreen` 第二次编译 1.6 分钟 = 缓存命中 | ❌ 误读——`bootloader.bin` 是构建**后期**才写的，不能当起点 |
| 复制 `core/*.o` 到别的 sketch 目录就能复用 | ❌ 下一轮编译会把这个目录清掉 |
| GxEPD2 只编用到的驱动 | ❌ Arduino 把库 `src/` 下**所有** `.cpp` 都编（104 个） |

**真正有效的只有"让编译器少编点东西"**：

1. GxEPD2 瘦身：**104 个 .cpp → 2 个**（只留 `GxEPD2_EPD.cpp` + `gdey/GxEPD2_154_GDEY0154D67.cpp`）。
   脚本 `tools/trim_gxepd2.py`（默认空跑，`--apply` 执行，`--restore` 完全还原）。
   安全核对：没有 .h 去 `#include` .cpp；保留的两个文件只引用自己和基类；基类实现只在 `GxEPD2_EPD.cpp`。
   ⚠️ **没有替用户执行**（动的是 `Documents\Arduino\libraries` 里的文件），也**未实测**。
2. 杀软排除目录（需管理员）
3. 少编译几次（先用预览器定排版）

另外确认了一件事：**编译期间 GxEPD2 的 libsdetect 阶段会给每个库 .cpp 生成 `.libsdetect.d`**，
也就是每个库文件要跑两遍（依赖探测 + 真编译）——这让"瘦身"的收益比预想更大。

### ② 部分行过长、换行后与下一行重合 → 根因是量宽度用错了字体

`buildLines()` 跑在 `setFont(&FreeSans9pt7b)` **之前**，
所以 `display.getTextBounds()` 量的是**内置 5×7 字体**（~6px/字），
而实际渲染用 FreeSans9pt7b（小写 ~10px/字）→ **宽度被低估近一半**
→ 以为塞得下 → 实际溢出 → Adafruit_GFX 自动换行
→ 换行用的行距是字体 `yAdvance`（22px）而非 `LINE_H`（16px）→ **压到下一行上**。

**三保险修复**：
1. 新增 `textWidth()`，直接读字体表 `xAdvance` 算宽度（与渲染宽度完全一致，与当前字体无关）
2. `buildLines()` 前先 `setFont()`
3. `display.setTextWrap(false)` 兜底（宁裁不折）

`BODY_MAX_W` 186 → **188**（= 200 − 6 − 6）。

### ③ 翻页后要等 2 秒按才有效、快速按无效 → 轮询在刷新期间是瞎的

全刷 2 秒里 `loop()` 卡在 `display.nextPage()`，**轮询根本读不到按键**。

**修复**：PWR / BOOT 都挂 GPIO 中断（`CHANGE` + 30ms 去抖），
按下/松开各记时间戳，刷新结束后 `loop()` 消费事件 → **刷新期间按的键一个不丢**。
同时把 `takeEvents()` 封装成"取完即清"，开机 3 秒缓冲结束时丢弃期间攒下的边沿。

### ④ 想要"上传前先看效果" → 做了 PC 端排版预览器

**`tools/preview_paging.py`**，输出 `01_Paging/preview/`（每页 PNG + 拼版图 + OFF 页）。

不是"大概模拟"，是像素级一致：排版参数和正文**直接从 .ino 解析**，
折行算法 1:1 照搬，字符像素**从 Arduino 库的字体头文件里读**
（`FreeSans9pt7b.h` 的 bitmap/glyph 表；页脚用 `glcdfont.c`），
按 `Adafruit_GFX::drawChar` 的同一套位图规则画点。

**加了双向对账机制**：固件开机串口打印
`layout: N lines -> M pages maxw=X/188 over=0 chk=0x----`，预览器打印同一行，两行一致即证明一致。

预览实测：**105 行 → 12 页，maxw=188/188，over=0，chk=0xA461**。

### 这一轮新增的"防再犯"机制

- 固件开机自检并打印 `over=`（超宽行数），**超宽不再靠眼睛发现**
- 排版参数集中在文件头 `#define`，预览器直接读，**改一处两边一起变**
- 页脚从 33 字符缩到 29 字符（`PWR:next  BOOT:prev  HOLD:off`），
  33 字符 × 6px = 198px 会出屏

## 用户贴了 AI 同僚的"电子路书"架构方案（17:18）

### 5 个实测不成立

1. **emoji/箭头全部不显示**：⛰🍼⚠⚡🏁🥤↱←↳ 全部 U+2000 以上，
   FreeSans9pt7b 只覆盖 0x20-0x7E，**画不出来**。结论：V0.1 必须用 ASCII 缩写
   （TURN/GLU/CLM/COBBLE/DANGER/SPRINT/FINISH），图标作为 V0.2 自制位图。
2. **连中点·和长横—都没有**（U+00B7、U+2014），这些看起来"基本符号"的其实
   都不在 ASCII 范围。结论：用 "." 代替 "·"。
3. **中文标题"南京环陵路"画不了**，需要点阵字库（U8g2 wqy12），是独立的工程
   阶段。结论：V0.1 标题用英文/拼音（如 "NANJING LOOP"），中文作为第 2 步。
4. **等宽字体 FreeMono9pt7b 全部超宽**：每行 209px > 188px，**数字右对齐的
   方案不可行**。只有 FreeSans9pt7b（171px）和 FreeSansBold9pt7b（175px）能塞下。
   12pt 字体全部超宽。
5. **手打空格做右对齐是假的**：非等宽字体空格宽度 ≠ 字符宽度，图上明显
   右列参差不齐。结论：渲染器必须**测宽右对齐**（用 glyph xAdvance 算字符串
   宽度，再 setCursor 到 EPD_W - BODY_X - w）。

### V0.1 实测可行的参数

- 字体：**FreeSans9pt7b**（或 Bold 版）
- 行高 **26**（> 字体 yAdvance=22 留 4px 余量）
- 每页 **6 行**（40 + 5×26 = 170 < 178 页脚线）
- 最宽行 171px（"35.8 km  CLM 4.2 km"）
- 页眉 30 + 横线 + 6 行 + 页脚 1 + 22 = OK

### 架构建议（与同僚方案的差异）

- **数据用 C 结构体数组**写死在固件（V0.1），不上 JSON
  - 理由：JSON 解析要 ArduinoJson（+ 编译时间，+ 库依赖，+ Flash），V0.1
    只验证"渲染器能不能画出好 UI"，数据源在哪不重要
  - 真正"换路线不用重烧"是 V0.2（SD 卡 / USB / BLE）
- 渲染器必须**测宽右对齐**（不能用字符串拼接）
- 不做 BLE（先 USB 都不做），V0.1 路线就烧在固件里

## 澄清"JSON 在哪实现"这个原理问题（17:50）

用户问：哪段代码实现了"JSON → 模板填充"。

**关键澄清**：单片机里 **0 行 JSON 代码**（.ino 搜 json = 0 结果）。
JSON 只活在 PC 侧，烧录前就被 `roadbook_gen.py` 翻译成 C 数组。

**三段职责（下次被问到直接引用）**：
1. `sample.json` — 人写的数据（浮点、英文 type 名）
2. `tools/roadbook_gen.py` 第 81–92 行 — **唯一的"JSON 相关代码"**，干两件事：
   - `"climb"` → `2`（TYPE_INDEX，单片机不认英文）
   - `22.6` → `226`（定点整数，避开浮点）
3. `02_Roadbook.ino` — 模板
   - 尺寸常量：第 34–42 行（MARGIN/HEADER_Y/BODY_TOP/ROW_H/MAX_ROWS）
   - 骨架+填数据：第 108–147 行 for 循环
     （MARGIN+ROW_H = 模板写死；RB_EVENTS[i] = 数据随路线变）

**V2 换 SD 卡数据源时只需改 1 行**：`pgm_read_byte(&RB_EVENTS[i].type)` → `events[i].type`，
下面 5 个 type 分支一个字不动。这就是分离的价值。
