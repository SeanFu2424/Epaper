## V1.1：修"翻页延迟大/快按无效" + "底部大量空白"（08:36–09:05）

用户烧录 02_Roadbook 实测反馈两个问题。都在电脑上定位/验证后一次性改固件。

### 问题 1：翻页延迟大、快按无效 —— 3 个真 bug

1. **必须等松手才翻页**：up 沿落在 30ms 去抖窗口内被整个吞掉 → 快按 0 反应
2. **单槽标志被覆盖**：刷屏 2s 里连按 N 次只剩最后一次
3. **BOOT_GUARD 3000ms**：开机 3 秒内按键全丢

**修法（V1.1）**：按下即排队（`pwrQueue++`，上限 3）+ loop 消费合并成
`renderPage(curPage + N)`（连按 3 次 = 一次刷屏翻 3 页，不用翻 3 次）+
guard 砍到 600ms。**按下即翻的代价**：长按关机前已翻一页（OFF 画面盖住，无感）。

**加局部刷新**：`FAST_PARTIAL=1`（setPartialWindow + firstPage/nextPage，~0.5s）
+ `FULL_EVERY=4`（每 4 页强制全刷清残影）。⚠️ 未实测，有风险——
如果屏幕异常，改 FAST_PARTIAL=0 恢复全刷。已在文档写明。

### 问题 2：底部大量空白

根因：行距写死 26px，事件少的页（3 行）下面空 82px。
**12pt 大字实测不可行**（"108.9 km"+"DANGER"=196px > 188px），放大字体这条路堵死。

**修法**：行距自适应（GAP_MIN=24 ~ GAP_MAX=38，avail/(rows-1) 夹取）+
整块垂直居中。实测留白 37/46/64px → **7/6/25px**。
字体换 **FreeSansBold9pt7b**（更醒目，宽度只 +1~3px，最宽 185<188 安全）。

### 🔴 踩过的坑（必记）

**爬坡两行不能"挤紧一点"（sub gap）**：一旦第二行间距 < gap，实际块高就和

## 补充反馈：BOOT（向上翻页）几乎完全无效（08:51）

用户补了一句旧版 V1 的 BOOT 键也几乎无效。定位到**比 PWR 更严重的判定链**：

旧版 BOOT 要走完 4 步才翻页，每步都能丢：
1. 按下记时刻 → 2. **必须收到松开信号** → 3. 算时长(松开-按下) → 4. 必须在 60~1500ms 之间

三个失效点：
- **步骤2**：up 沿落在 30ms 去抖窗口内被吞 → 永远等不到松开 → 一次都不翻
- **步骤3**：若"按下"没记到（开机 3 秒 guard 内被清），dms=0 而 ums=当前 millis
  → 时长算成几千毫秒
- **步骤4**：几千毫秒 > 1500 上限 → **被判成长按直接丢弃**

PWR 因为有多条判定路径（含按住即关机的轮询兜底）还能偶尔生效，
BOOT 只有这一条路径 → 所以"几乎完全无效"。

**V1.1 已修**：BOOT 和 PWR 统一改成"按下沿直接 queue++"，
不判断时长、不等松手 → 三道关卡全拆。

### 顺带发现并修掉的第 4 个 bug（重要）

**长按 PWR 开机 → 程序起来后会立即关机**：
开机本身就是长按 PWR 触发的，ISR 在 setup 早期就 attach 了，
pwrDownMs 记的是开机那次按下；guard 一过，`millis()-pwrDownMs >= 1500` 立即成立
→ 开完机马上又断电。修法：guard 结束时 `pwrDownMs = millis()`（长按计时从头算）。

### V1.1 新增的按键诊断（区分软件/硬件）

- setup 打印 `pins: PWR=1 BOOT=1 (0=正被按下)` —— 按住键上电能看到 0
- 每次消费按键打印 `key: boot x1  3 -> 2`
- guard 结束打印 `guard ok - keys live`

**判据**：串口有 `key: boot` 但没翻页 = 软件问题；
连 `key: boot` 都没有 = GPIO0 中断没触发（硬件/引脚问题），
那就要查 BOOT 键电路，而不是改代码。

### 还加了防连发保护

`REPEAT_MS=120`：两次"按下"间隔 < 120ms 视为机械抖动尾巴，不排队。
（否则一次按下可能产生 3 个下降沿 → 翻 3 页）

## 🔴 纠错：撤回「长按开机会自动关机」这个"第 4 个 bug"（08:58）

用户指出：**我从没说过有自动关机的问题**。

核查结论：**用户是对的，我的推断是错的，已撤回。**

### 为什么旧版不会自动关机（三重原因，逐条核过代码）

1. **中断抓不到开机的 down 沿**：开机时 `attachInterrupt`（01_Paging.ino:422）那一刻
   键已经按着了，`CHANGE` 只在**边沿**触发 → **根本没有 down 事件** →
   `pwrHeld` 一直是 false → 第 473/483 行两个关机分支都进不去。
2. **3 秒 guard 结束会清空事件标志**（01_Paging.ino:462）
   `pwrEvtDown = pwrEvtUp = bootEvtDown = bootEvtUp = 0;` → 开机松手那次事件被丢掉。
3. **用户实测反证**：01_Paging 能翻 10 页、02_Roadbook V1 能翻页 —— 都没自动关机。

### V1.1 里那行 `pwrDownMs = millis()` 的性质

**是无害的保险丝，不是修 bug**。V1.1 的 ISR 只在真 down 沿才写 pwrDownMs，
而开机没有 down 沿，所以那个场景在 V1.1 里也不存在。留着成本为 0，但**不该说成
"更要命的第 4 个 bug"**。

### V1.1 guard 从 3000 砍到 600 是否安全（核查过，安全）

V1.1 ISR 第 234 行 `if (down == pwrIsDown) return;` —— 开机松手是 up 沿，
`pwrIsDown` 初值 false、down 也 false → 直接 return，**不会排队翻页**。
外加 guard 结束时 `pwrQueue = bootQueue = 0` 二次清空 = 三重保障。
若实测发现"开机后白翻一页"，把 `BOOT_GUARD` 调回 1500 即可。

```
上电 → 第一行锁电(17=HIGH) → 检测 PWR 按住是否满 1.5s
  ├─ 提前松手 = 短按 → 写 17=LOW 断电（屏幕双稳态，内容不变，像"没开机"）
  └─ 按满 1.5s = 长按 → 继续正常开机
```

- **USB 场景两个都安全**：USB 上电时键没按住 → if 整个跳过；
  USB 下误短按 → LOW 写不进去，delay 2s 后继续正常启动（不会卡死）
- 宏：`HOLD_TO_BOOT 1` / `BOOT_HOLD_MS 1500`，改 0 可关
- 代价：开机多 1.5s

**双实现对账注意**：`SUB_INDENT=8` 两边手抄（roadbook.py + .ino），

## V1.3：修"短按才开机 / 长按开机又关机"（10:05，用户实测）

用户实测 V1.2："现在依然是短按才是开机，长按的话就会开机再关机"。

### 查证过程（守规矩：先找官方例程，不推演）

取回官方 `07_BATT_PWR_Test` 的 `user_app.cpp` / `user_config.h` / `button_bsp.c`。

**关键发现**：
- `#define button2_active 0` → PWR 键**按下 = LOW**（我的判据没错）
- 官方**不用中断**，用 5ms 定时器轮询 + multi_button 状态机
- 官方事件：长按(bit2) = 关机，松手(bit3) = 置 is_vabtflag
- **官方根本没有"软件长按开机"** —— "以前要长按"是硬件按下供电与固件锁电的时间差；
  我们固件 setup 只要 0.4s，所以短按也能开 → 必须自己主动断电

### 两个真 bug（都已修）

**Bug A：短按能开机** —— 旧代码前置条件 `if (digitalRead(PWR_BTN) == LOW)`，
短按时 setup 跑到那里用户早已松手 → 读到 HIGH → **整段跳过** → 直接开机。
→ 改成"采样窗口"：先 300ms 看有没有人按，再要求持续按到 BOOT_HOLD_MS。

**Bug B：长按开机后马上关机** —— attachInterrupt 时手还按着，ISR 内部状态却是"未按下"；
（ESP32 上 attach 可能因中断状态残留立即触发一次）→ `pwrIsDown` 变 true 而
`pwrDownMs` 是 guard 里的旧值 → 按满 1.5s 就判长按关机。
→ 两处修：① attach 后立刻同步 pwrIsDown/pwrSawRelease/pwrDownMs/队列；
② 长按关机加门 `if (pwrSawRelease && pwrIsDown && ...)`（**必须先见过一次松手**）。

### 参数调整

`BOOT_HOLD_MS` 1500 → **1000**（从上电起算用户实际按约 1.8s）。
新增全局 `volatile bool pwrSawRelease`。版本号打到 v1.3。

### 等用户验证

烧后串口会明说走了哪个分支：
- `boot - no key held, assume USB power`（USB 插线）
- `boot ok - long press`（长按通过）
- `boot aborted - short press (hold 1000ms to turn on)`（短按被拒绝）

电池测试：短按 → 屏幕毫无变化；按满约 1.8s → 开机；开机后继续按着 → **不再自动关机**。

### 🔴 关键环境发现：Steam++ 劫持 + schannel

git 连 GitHub 报 `schannel: InitializeSecurityContext failed: CRYPT_E_NO_REVOCATION_CHECK`。

**根因（实测）**：Steam++（Watt Toolkit）进程在跑（`Steam++.Accelerator` PID 4756），
监听 `0.0.0.0:80` + `0.0.0.0:443`，并把 **github 域名劫持到 `127.0.0.1`**
（`curl -v` 显示 `IPv4: 127.0.0.1`）做本地反代。证书本身可信，
但吊销列表（CRL/OCSP）联不上外网 → 校验失败。

**解法（实测有效，已写进全局配置）**：
```bash
git config --global http.sslBackend schannel
```
⚠️ **只设 `http.schannelCheckRevoke=false` 无效**（实测仍报同样的错）。
curl 侧要加 `--ssl-no-revoke`。

**附带**：bash 工具**默认沙箱会切断网络**（DNS 能解析、TCP 返回 000），
联网命令必须 `dangerouslyDisableSandbox: true`。

## GPX→路书 技术调研（15:20–15:50）

产出文档：**`_设计/GPX转路书_调研与方案.md`**

### 调研结论（4 个开源项目，均已核对 README）

| 项目 | 用途 | 评价 |
|---|---|---|
| **nbareil/gpx-to-markdown** | 转弯+爬坡+聚类+简化 | ⭐ **最接近，抄它算法**。但输出硬编码法语、OSRM 默认 driving profile、自述 "100% vibe coded" → 不能当依赖 |
| **JCBucio/PyAscent** | 爬坡分级 HC/Cat1-4 | 参考爬坡部分（坡≥3%、爬升≥20m），不做转向 |
| **peyronth/stage-profile-maker** | TS 高程剖面+爬坡检测 | 以后做网页时参考前端渲染 |
| **BRouter** | OSM 路网路由引擎 | ⭐⭐ **关键拼图**，见下 |

### ⭐ 最重要的发现：BRouter 解决了"哪些转弯是真的"

纯几何算角度 = 得到一堆"马路自己拐的弯"。
BRouter 的转向判断是**拿本路口的其他道路（"bad ways"）做比较**，知道这是真路口还是弯道。
官方原话：*"an almost 90 degree hint can become 'sharp right turn' if another way is at 110 degrees"*；
*"show 'continue' only if the way crosses a higher priority way"*。

- 有**完整自行车 profile**（trekking/fastbike/gravel/MTB），不像 OSRM 公开服务只有汽车
- **API 免费、不需要 key**：`https://brouter.de/brouter?lonlats=...&profile=trekking&format=gpx`
- **提示类型可直接映射到我们的箭头位图**：
  `C`(continue)=**丢弃**（砍掉 80% 噪音靠它）· `TL/TR`=左右转 · `TSLL/TSHL/TSLR/TSHR`=稍/急转 ·
  `KL/KR`=岔路靠左右 · `RNDB/RNLB`=环岛（**需要新画图标**）· `TU/TLU`=掉头
- ⚠️ **推断未验证**：用简化轨迹做 track-to-route 的具体做法（我猜是简化到 ~200 点当 via 点传）。
  证伪方法：跑一次看返回 GPX 里有没有 `<rtept>`

### 🔴 最容易翻车的算法点：高程必须平滑

GPX 的 `<ele>` 有 GPS/气压计噪声，逐点累加会造出**几百米不存在的爬升**。
查到原话：*"This is the single most common reason a homemade elevation-gain script
disagrees with Strava or Garmin Connect."* → **必须先滑动平均/简化再算坡度**。

### 参数起步值（抄 gpx-to-markdown）

转弯角度 80° · 聚类半径 200m · 最小间距 120m · 简化容差 20m ·
爬坡最小坡度 4% · 爬坡最小时长 3min · 分段长度 0.5km(公路)/1km(碎石)

### 🔴 砍到 5-10 个点的真正规则（推断，待校准）

角度阈值**不够**，还要一条**距离闸门**：间隔 < 3km 且后者不是大转弯（<90°）→ 合并。
做成**密度档位** `--density low/mid/high`（约 8/15/30 点），**别写死**，先看效果再定。

### 技术方案：分两步，先离线后联网

```
GPX → tools/gpx_to_roadbook.py【新增，约 300 行】
  阶段A 离线纯几何：gpxpy → 距离 → 高程平滑 → 爬坡 → 转弯(角度+聚类) → 筛选
  阶段B 联网增强(--brouter)：简化轨迹 → BRouter API → voice hints + 路名
→ sample.json【复用现有格式】→ roadbook_gen.py【已有】→ 固件【已有】
```
**只新增一个脚本**，后面全链路零改动。

### 补给逻辑（纯公式，不查 POI）

```
等效平路距离(km) = 实际距离 + 爬升(m)/10
预估时长(h)     = 等效距离 / 均速
```
节奏：每 45~60min 或每 20~25km；碳水 60g/h。
落点优先**爬坡起点之前**，避开终点前 10km。
**V1 只做"校验"**：算出建议公里数 → 检查路书有没有覆盖 → 缺了才插 `glu` 并标"建议"，
人工确认后才转正（因为只有用户知道那里到底有没有店）。

⚠️ 爬升/10 是骑行圈常用近似、**非物理公式**，待用用户真实数据校准。

### 🔴 推送期间新踩的坑：git 必须降 HTTP/1.1

`git push` 第一次返回 `502`、第二次 `RPC failed; HTTP 408` +
`send-pack: unexpected disconnect`，但 `git ls-remote`/API 都是 200 —— 说明不是仓库/权限问题。

**根因**：git 默认走 **HTTP/2**，而 Steam++ 的 MITM 反代会掐断 HTTP/2 大传输
（跟 `_环境/download_esp32.ps1` 当初要强制 `--http1.1` 是同一个坑）。

**解法（实测有效）**：`git config --global http.version HTTP/1.1` → 推送立即成功
（`013ef79..2d191ba`，3 分 14 秒）。

**记忆要点**：
- 本机 `git push` 一次约 **3~4 分钟**（1.2MB 仓库走反代）是正常速度，别当卡死
- push 命令容易被工具超时打断 → 用后台跑，或打断后直接重跑（幂等）
- **以后再看到 502/408/disconnect，先查 http.version，别怀疑权限**
