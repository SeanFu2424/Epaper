# 2026-09-07

## 墨水屏骑行路书 V1 工具链

基于 `EinkRoadbook_Kit (1).zip` 的规划文档，落地了 V1 MVP 的完整工具链：

- `tools/render_roadbook.py` — Python+Pillow，路书 JSON → 200×200 1-bit 位图 → 打包成 SD 卡用 bin
- `tools/verify_bin.py` — 校验 bin 头部格式、尺寸、CRC32
- `firmware/EinkRoadbook_V1/EinkRoadbook_V1.ino` — ESP32-S3 固件：SD 卡读 bin → 按键翻页 → deep sleep 维护刷新
- `samples/roadbook_sample.json` — 12 个事件的路书示例
- 输出 `out/roadbook.bin`（37 页，180.7 KB）+ 每页 PNG 预览 + 拼版图

设计要点：
- 板子是 ESP32-S3 + 1.54" 200×200 墨水屏（SPI）
- 不用板载字库，所有中文在 PC 端渲染成 1-bit 位图
- bin 格式：16 字节头（magic+version+flags+width+height+count+crc32+reserved）+ N×5000 字节
- bit1=黑 极性，与 GxEPD2 BW 类的 drawBitmap 约定一致
- 固件用 ext1（GPIO 0-21 唤醒）+ 30 分钟定时器全刷
- 按键 BTN_NEXT=0（BOOT 键注意上电不按住）

## 关键坑

- Pillow `ImageDraw.text` 的 `anchor` 参数在 12.x 里行为有点反直觉，"ma" 不是垂直居中；用 "mt" 显式指定更稳
- struct pack 后文件头长度必须真的等于 HEADER_SIZE，否则固件按错偏移会读到垃圾
- 板子未到手时把"硬件配置"段全部用宏抽出来比硬编码好改

## 硬件确认（微雪官方资料，已核实）

板子 = **ESP32-S3-ePaper-1.54**（黑白版，非 G 版四色）

| 信号 | GPIO |
|---|---|
| EPD_PWR (EPD3V3_EN) | 6 —— **LOW=开屏电，最容易漏** |
| EPD_BUSY | 8 |
| EPD_RST | 9 |
| EPD_DC | 10 |
| EPD_CS | 11 |
| EPD_SCLK | 12 |
| EPD_MOSI (SDI) | 13 |
| BOOT 键 | 0 |
| PWR 键 (BAT_KEY) | 18 |
| SD 卡 | 39 CLK / 40 MISO / 41 MOSI |

- 面板 **GDEY0154D67**，200×200，驱动 IC **SSD1681**，支持局部刷新
- GxEPD2 驱动类：**`GxEPD2_154_GDEY0154D67`**（备选 `GxEPD2_154_D67`）
- 版本差异：V1 = ESP32-S3FH4R2（4MB Flash + 2MB PSRAM）；V2 = ESP32-S3-PICO-1-N8R8（8MB + 8MB），2025-11 起出货，**示例不通用**
- arduino-esp32 需 ≥ 3.2.0（教程用 3.3.10），GxEPD2 用 1.6.9

**两个大坑**
1. GPIO6 屏幕电源必须手动 `digitalWrite(LOW)` 拉低，GxEPD2 不管这个脚。漏了 = 串口正常但屏幕死白
2. 屏幕接的是 SCK=12/MOSI=13，而 ESP32-S3 默认 SPI 的 MOSI=11、SS=10 → 必须 `SPI.begin(12, -1, 13, -1)` 重映射，直接 `display.init()` 不亮

## 板子版本确认：V2

用户已确认是 V2（ESP32-S3-PICO-1-N8R8，8MB Flash + 8MB OPI PSRAM）。

**V1 vs V2 板卡参数差异只有一个点：PSRAM 类型**
- V1 → QSPI PSRAM
- V2 → OPI PSRAM

Flash Size 都是 4MB (32Mb)，分区方案都是 "Huge APP (3MB No OTA/1MB SPIFFS)"。
（来源：微雪 GitHub `waveshareteam/ESP32-S3-ePaper-1.54/02_Example/Arduino/Tools Configuration.png`）

之前文档里写的"V2 选 8MB"是错的——已修正。选 4MB 跟分区方案匹配，不损失功能。

**DeepWiki 的引脚表是 AI 生成的幻觉**，不可信。引脚表以官方 `user_config.h` 为准（见上方表格）。

## 用户环境：装 esp32 板卡包失败（GitHub 超时）

报错：`13 INTERNAL: Download failed ... crosstool-NG ... xtensa-esp-elf-14.2.0_20260121-x86_64-w64-mingw32.zip ... wsarecv 连接失败`

**根因**：GitHub 直连被墙。esp32 3.3.11 板卡包共 **17 个文件 1803 MB**，板卡管理器逐个从
github release 下载，任一超时就整体失败。

**已验证的事实**
- 我这边（沙箱）也测过：github.com、raw.githubusercontent、dl.espressif.cn/.com、
  mirror.ghproxy、gh-proxy、清华/USTC 镜像 → **全部 000 不通**
- arduino.me 的 esp32 镜像 index 已失效（返回 SPA HTML，不是 JSON）
- 可用通道：**jsdelivr CDN 通**（用它拿到了官方 `package_esp32_index.json`）
- 用户的 `Arduino15/staging/packages/` 里已有 AVR 包 → 说明 IDE 本身联网正常，只是 GitHub 不通

**1803 MB 的构成**（3.3.11）
- S3（Xtensa）真正需要 659 MB / 8 个：core、esp-x32 编译器 394MB、esp32s3-libs、
  esp32-libs、xtensa-gdb、esptool、openocd、mklittlefs
- 用不到 1144 MB：esp-rv32 RISC-V 工具链 673MB + riscv-gdb 43MB + c3/c5/c6/h2/p4/s2-libs 427MB
- 板卡管理器无"只装部分"选项，必须全下

**产出**：`_环境/download_esp32.ps1`
- 17 个文件的 url + sha256 + size 硬编码（从 jsdelivr 拿的官方 index 解析）
- 下到 `%LOCALAPPDATA%\Arduino15\staging\packages\`，IDE 会复用缓存跳过下载
- curl.exe `-C -` 断点续传，重试 5 次，SHA256 校验，失败文件下次跑自动补
- `.\download_esp32.ps1` 默认只下 S3 必需 659MB（验证网络）；`-All` 下全部

**给用户的三条路**：① 配代理 / Watt Toolkit 加速（推荐）② 跑脚本 ③ 迅雷手动下放 staging
