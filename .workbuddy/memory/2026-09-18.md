### 🐛 修掉一个真 bug：HALFWAY 倒挂
**现象**：第 2 页出现 `76.2 CLM 3.2 / 79.4 ★★` 之后跟一行 `77.7 HALFWAY`
—— 77.7 比 79.4 小，读者会以为写错。

**根因**：原有"避开拥挤"逻辑是"从真中点一路 +0.4 往后找"，它只在开头检查过了
`_in_climb()`，中途会**跨过爬坡起点钻进爬坡区间内部**。爬坡占两行、第二行显示的
是"结束公里数"，所以区间内的事件必然倒挂。

**修法**：改成**候选扫描** —— 真中点 ±8km 每 0.4km 撒候选，过滤掉
①爬坡区间 ②与邻近事件距离 <1.2km，然后**取离真中点最近的那个**。
本案例：77.7 → **74.9**（移出 76.2~79.4 区间），偏离真中点仅 0.4km。

⚠️ **这个 bug 覆卮山那条恰好没触发**（那条的中点没落进爬坡区间），
所以是新路线才暴露出来的。以后加新路线都要看一眼有没有"数字倒挂"。

### 爬坡第二行拥挤：省略 " km" 单位
三位数公里数时放不下：`136.2 km`(72px) + 间距(4) + `5.5%`(40) + 5星(65) = **181px**，
而可用宽度只有 188 - 8(缩进) = **180px**。差 1px，导致 `136.2 km` 和 `5.5%` 粘连。

试过的方案与结论：
- ❌ 缩小星星：13px 已是可辨认下限（12px 尖角就糊，11px 更差），省不了
- ❌ 坡度整数（5.5%→5%）：丢精度
- ❌ 减缩进：视觉上"从属感"会消失
- ✅ **第二行省略 " km"**：省 20px，**不损失任何数字精度**（小数点照留、坡度照留一位小数）

### 密度问题：150km 路线默认 14 个事件太少
默认 `--max-events 14` 被 4 段爬坡（占 8 行）+ 4 个补给点吃掉，
**只剩 4 个转弯提示**（150km 山路）。用 `--max-events 18` 后 → 8 个转弯、4 页。

**待用户确认**：是否把"事件上限按距离自适应"做成默认（如 `距离/8` 夹在 12~26）。

### 🐛 顺带查出并修掉：爬坡结束公里数差 0.1 km
屏幕上"结束公里数"是 `km + length` 反算的，之前**起点和长度各自 round 到 1 位**，
相加就与真实终点错开 0.1：
- `真实 30.2133 + 18.3444 = 48.5578 → 应显示 48.6，实际印成 30.2 + 18.3 = 48.5`
- `真实 124.7131 + 11.5440 = 136.2571 → 应显示 136.3，实际印成 124.7 + 11.5 = 136.2`

**修法**（`gpx_to_roadbook.py`）：先 `end = round(km + length_km, 1)`，
再 `length = round(end - km, 1)` 反推。这样屏幕上的 `起点 + 长度` 必然等于终点，读者能自己验算。
副作用：CLM 18.3→18.4、11.5→11.6（更准了）。
⚠️ 这个 0.1 误差**只在预览图里才能看出来**（PC 端和固件端都用 JSON 里那两个数算），
CLI 打印以前只打 length_km 真实值，所以一直没暴露。顺手把 CLI 报表改成
"起点 → 终点 / 长度"三数都打。

## 第三轮：6 页文字核对 → GLU 改成按时间铺

### 起点
先按用户要求把 6 页版**文字**逐行交付核对（25 事件 / 32 行 / 6 页，含 CP/合并行）。
用户看完回：**"其他没有问题，爬坡也可以先不变，但 GLU 补给的时间和距离位置与网站偏差比较大"**。

### 根因一（实测，非推断）
用 pymupdf 按坐标还原网站 PDF，拿到它全部 13 个补给点：
GEL 8 个（18.4 32.3 45.2 68.2 94.7 114.4 126.6 140.0）+ H₂O 5 个（40/60/80/100/120，均匀 20km）。

用速度模型把两边点位都投到时间轴上：

| | 里程间隔 | 时间间隔 |
|---|---|---|
| 网站 GEL | 13.9 / 12.9 / 23.0 / 26.5 / 19.7 / 12.2 / 13.4 | 30 / 44 / 41 / 59 / 37 / 29 / 40 分钟 |
| 我们（按里程 13km） | 恒定 13.0 | **25 / 78 / 18 / 58 / 24 / 23 / 68 分钟** |

→ 结论：**网站按时间铺，我们按里程铺**。所以我们"平路 19 分钟就提醒一次、爬坡 79 分钟才轮到一个"。

### 根因二：爬坡禁区会吃掉提醒
Far02 的 30.2~48.6 是**一整段 18.4km 连续爬坡**（模型约 1 小时）。
"爬坡块占两行 → 块内不放任何事件"这条规则，让这一小时里**一个提醒都放不下**，
这就是 79 分钟空档的来源。
（网站没这个约束，它的 32.3 / 45.2 / 126.6 三点恰好落在我们的爬坡块内部。）

### 改动（提交 4184633）
1. `time_axis()` 速度模型：坡度→速度经验表（平路 32、5% 坡 18、9% 坡 11.5…），
   把"距离-高程"剖面换算成时间轴；`--speed-scale` 整体缩放。
   ⚠️ 经验值不是实测：Far02 算出来全程 5h34，网站页眉 9h39（后者大概含休息）。
2. `--fuel-mode {km,time}` 默认 **time**；time 模式下 `--fuel-interval` 单位是**分钟**（默认 40）。
   km 模式与旧版 **diff 完全一致**（回归通过）。
3. `--glu-in-climb`：放行爬坡块内部；坡内的 GLU 标 `sub=1` → 左列缩进 8px。
4. 事件结构体加 `sub` 字段，`preview_roadbook` / `roadbook_gen` / `02_Roadbook.ino` 三处同步。

### 效果（Far02，GLU 9 个）
时间间隔 25/78/18/58/24/23/68 → **33/36/35/35/34/34/35/39 分钟**；
与网站点位 RMS 5.7km → **3.3km**（8 个点里 6 个误差 <2.3km）。
